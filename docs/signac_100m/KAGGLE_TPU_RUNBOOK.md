# Kaggle free TPU qualification runbook

Notebook: `notebooks/SIGNAC_100M_KAGGLE_TPU_PREFLIGHT.ipynb`.

The notebook targets Kaggle's free TPU accelerator with an eight-device requirement. Receipts record TPU device type and counts plus software/platform metadata, but do not identify the chip SKU or Kaggle image/build. Preserve the accelerator and runtime details shown by the Kaggle session when reporting target-specific results; availability and runtime images can vary. The notebook runs bounded synthetic multi-device model updates. It contains no research training campaign. A successful canary qualifies engineering plumbing only; it does not authorize the production trainer.

Rank-local model setup, parity work, forward/backward updates, restart-state capture, and checkpoint writes pass through XLA status votes before workers enter later collectives or barriers. The gradient reducer also votes on identical parameter/gradient layouts. These checks turn ordinary rank-local Python or asynchronous device-stage failures into a shared canary failure; they do not guarantee recovery from a failed XLA collective or runtime process failure.

## Run

1. Select the free TPU accelerator in Kaggle. Run repository discovery; it must resolve exactly one snapshot.
2. Run the environment and static contract cells. M102 must report exactly 101,790,080 parameters. The static launch gate remains `BLOCKED` until corpus, evaluation, and target evidence exist.
3. Run the all-core canary cell. It starts one fresh subprocess for each candidate. `torch_xla.launch` creates the worker group, and each worker acquires its device inside the launch function. The frozen check requires eight worker ranks and eight global TPU devices, four accumulated 4,096-token microsteps, and two synchronized updates. For M102, the notebook also requests a bounded restart check: rank zero writes the replicated model/Adam state after update one, every rank saves its CPU generator, rank-local XLA RNG state, and versioned synthetic stream cursor, then a fresh worker group restores them. It replays a random XLA probe from the saved state before update two and compares the resumed probe and final XLA RNG state with the uninterrupted path. If Kaggle grants another topology or the runtime API check fails, keep the failure receipt and stop.
4. For the throughput/headroom gate, set `RUN_M102_QUALIFICATION = True` in the notebook cell. This adds an M102 profile with 21 total updates: the first update includes compilation and the next 20 provide measured steady-state critical-path timings. The aggregator requires an XLA `peak_bytes_used` and `bytes_limit` sample after every update on every rank, and blocks if any rank's observed peak exceeds 85% of its reported device limit. Older runtime images that omit peak counters remain useful for the smoke canary but cannot pass this profile.
   To exercise the actual production backend and sampler with synthetic input, you may also set `RUN_XLA_DEVELOPMENT_CAMPAIGN = True`. `v5_training.kaggle_xla_development` runs one bounded update, starts a fresh worker group, restores the shared model/Adam checkpoint and per-rank RNG/cursor state, then completes update two. The profile is disabled by default, writes under Kaggle working storage, and remains unqualified engineering plumbing. It does not use research data, certify Kaggle Output durability, or authorize training.
5. Review each rank receipt and aggregate. Require one shared source-tree digest, matching nonempty Python/PyTorch/`torch_xla`/platform metadata, ordinals 0–7, PJRT TPU identity, a positive and rank-consistent addressable-device count, distinct per-rank synthetic sample streams, the expected all-reduce probe, passing FP32 and BF16-autocast tiny-model gradient comparisons against a single-device global-batch reference with unequal per-rank example counts, identical initialization and post-update M102 model hashes, identical Adam-moment hashes, matching optimizer steps, finite losses and gradient norms, compile-inclusive first-update timing, one bounded steady update, and memory counters when the image supports them. For the M102 restart, verify every rank-state file hash, each restored RNG-state hash and synthetic cursor, the resumed sample-stream suffix, matching runtime metadata, and final RNG/cursor/model/Adam state against the uninterrupted run. For qualification, check all 20 steady timings and the peak-memory ratio for all ranks.
6. The notebook writes `signac_100m_post_canary_preflight.json` after the all-core checks. It reads each raw M102 aggregate with its adjacent `rank-00.json` through `rank-07.json`, recomputes the aggregate from those ranks, and records every file hash. Valid smoke and optional qualification bundles become `PRESENT_FOR_REVIEW` evidence for inspection only. If you run preflight after downloading Kaggle Output, keep each aggregate beside its eight rank files and pass the raw aggregate paths with `--runtime-receipt` and, when present, `--qualification-receipt`. The production runtime gate remains blocked because the canaries use synthetic inputs and do not establish the complete G1-G4 production predicates.
7. Save the timestamped `signac_100m_distributed/` directory, static and post-canary preflight reports, source identity, aggregate receipts, runtime metadata, notebook, and source snapshot as Kaggle Output. Verify the saved artifact hashes after copying them out, and confirm each receipt's source-tree digest matches the attached snapshot inventory, including the launch notebook.

Each rank receipt also records Linux process-lifetime high-water RSS after each completed update and once after the canary's final parameter and Adam-moment hashes when `resource.getrusage` is available. The final sample observes host staging from those canary hashes, which run at initialization and at the end rather than after every update as in production. These values describe one worker process, may include earlier initialization/runtime allocations, and may double-count shared pages across ranks. They are diagnostic only: do not sum them as host-wide memory or treat them as a fit gate. The qualification gate still depends on per-rank XLA `peak_bytes_used` and `bytes_limit` counters, and production's repeated hash staging still needs target measurement.

The FP32/BF16 parity oracle is a tiny linear probe that tests reduction and global-denominator math; it does not establish numerical parity for the full Signac Transformer. The optional M102 restart is a controlled synthetic update-boundary check, not production exact-resume certification. It exercises per-rank CPU and XLA generator-state restore plus a synthetic stream cursor, but does not test the production packed-data bucket-lane sampler, Kaggle Output durability, or checkpoint round-trip from durable storage. The optional `xla-development` campaign exercises the production backend, sampler, and same-session fresh-worker-group checkpoint restore with synthetic input; it does not establish production parity, durable output, or research-data readiness. The 20-update profile records XLA allocator high-water counters for its synthetic workload only; it does not prove the production run fits or replace production throughput, memory, and restart gates. Production `execution="xla"` remains blocked pending target certification. Both development profiles are unqualified and do not authorize a research run.
