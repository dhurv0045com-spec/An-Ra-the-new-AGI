# ADVERSARIAL ARCHITECTURE REVIEW (final pass, §45)

Fresh hostile pass over the selected architecture, answering the ten required questions; revisions applied where the review demanded them.

1. **Which component has the weakest evidence?** The `~97M multi-seed formation replication` listed as a 500M precondition — it is a *plan*, not evidence; it correctly stays on the blocker list rather than being counted as satisfied. The PROVISIONAL optimizer/schedule fields are the weakest *adopted* items; both carry named revisit triggers.
2. **Which component adds the most complexity?** The EXPERIMENT_ONLY output treatments in `v5_next`. Review verdict: keep, but strictly gated — they encode the R1C family (independently mirrored by BRAMASTRA B04), cost ~40 lines, are constructor-gated, hash-visible, and tested to be inert on the canonical path. Deleting them would force new code at R1C-interpretation time under time pressure; the gate is the safer failure mode. No further knobs were added (§25): the contract has exactly one scientific switch (`output_mode`) plus the immutable EOS flag.
3. **Which component is hardest to falsify?** The family-level baseline (D1 "dense decoder-only"). It is unfalsifiable until a bottleneck is isolated — which is precisely why it is DEFAULT_BASELINE rather than LOCKED-as-superior, and why the spec never claims it is optimal.
4. **Which variable is being confounded?** None newly introduced. The audit explicitly refuses to de-confound R1/R1B's class-space effect by design change (that is R1C's job) and keeps the production-tokenizer task in CS-TRANSFER-001 on a regenerated, attack-screened surface so evaluator artifacts cannot masquerade as transfer.
5. **Which decision should actually remain unresolved?** Vocabulary size, tied-vs-untied output, and numeric atomization — all BLOCKED on R1C + CS-TRANSFER-001. The review confirms no legitimate way to freeze them today.
6. **What can be deleted?** Nothing in the reference implementation survives deletion review with fewer than: contract, receipt, treatments-gate, EOS lock — each is either the §38 authority or a §41 obligation. The planned separate training stack was deleted before it existed (IMPLEMENTATION_PLAN).
7. **What could data solve instead of architecture?** Formation (rank-1 bottleneck) might be data-surface-bound, not representation-bound — but CYR-011's full-exposure 0% on candidate-free held-out caps how far that explanation stretches; the honest answer is "R1C + transfer decide."
8. **What could evaluation error explain instead?** Part of the class-space effect cannot be excluded if the evaluator shares generator structure with training — CS-TRANSFER-001 therefore requires regenerated surfaces with independent attack screens, and its null branch (K03) is the falsifier for the effect itself.
9. **Is the winner meaningfully different from V5?** No — deliberately. It differs in governance (blocked-field enforcement, hash-visible treatment gating, readiness gate) and in two contract corrections already in V5. Per §32 it is named V5.1, not V6.
10. **Would we still build this with only one T4?** Yes — the entire plan is T4-shaped: all three required experiments total ≤ ~45 T4-hours, the canary is CPU-fixture-verifiable, and every blocked field avoids spending the one T4 on unresolved questions.

**Revisions made by this review:** (a) readiness JSON re-checked so no gate is marked SATISFIED without a runnable verification behind it; (b) the sensitivity note in CANDIDATE_COMPARISON was sharpened to state explicitly that B-over-A reversals require R1C *and* transfer evidence, not scoring noise; (c) the spec's claim ceiling was re-tightened to forbid "superior" language even between candidates.
