# Recursive improvement that can be distinguished from more training

The target is a learner that eventually helps improve its own learning procedure. This is an ambitious research capability, not an automatic consequence of collecting experience or repeatedly fine-tuning. Implement the provenance and measurement machinery now so that a future improvement can be attributed correctly.

## 1. Levels of improvement and who did the work

| Level | What changes | Required attribution |
|---|---|---|
| R0: ordinary acquisition | Weights gain a skill under a fixed human-designed method | Trainer, data and checkpoint identities |
| R1: continual acquisition | Additional skills with protected earlier performance | Acquisition/retention sequence, replay and full costs |
| R2: learned adaptation policy | The model selects useful practice, inquiries or adaptation actions | Learned policy decisions and matched fixed-policy controls |
| R3: learning-method improvement | A model-origin proposal improves future learning under a changed procedure | Proposal origin, compiled method, independent meta-evaluation |
| R4: recursive method improvement | An accepted successor uses the improved system to propose the next useful learning change | Generation chain, proposal quality and repeated independent gains |

Use these labels in reports. External Luna/Sol implementation is engineering assistance. It does not establish R3 or R4 for BRAMASTRA. A model-origin proposal must have a BRAMASTRA checkpoint hash, exact public proposal input, generated tokens/structured output, sampling settings and resource receipt. A human may approve it and a deterministic compiler may implement it without changing its meaning. If an external coding agent invents the substantive method, record mixed/external origin and restrict the self-improvement claim.

The proposal capture is produced by the controlled model-execution adapter, not accepted as a caller-supplied assertion. Its canonical transcript binds checkpoint payload identity, rendered input, tokenizer, RNG/sampling state, raw output bytes/tokens, parsed AST and parser/compiler versions. The validator reparses the captured output and compares the AST before compilation. For qualified reproducible decoding, a bounded replay through the identified checkpoint verifies the output under the captured settings, with cost charged; otherwise retain the controlled-run receipt and explicitly label replay verification unavailable. Hashes detect inconsistency, not independent proof that an arbitrary submitted transcript was generated by a model. Unverified external transcripts cannot receive model-origin qualification.

## 2. The object being improved

Represent a learner instance as `L = (theta, method, memory, curriculum, runtime_contract)`. `theta` is the shared decoder and declared heads. `method` describes objective weighting, admitted gradient transformations, optimizer/schedule settings and update boundaries. `memory` is a frozen admissible store/index identity. `curriculum` is the task/data selection rule and its state. The runtime contract fixes budgets, eligibility, checkpoint integrity and evaluation boundaries.

Every proposal declares exactly which components change. A new memory entry is not an optimizer improvement. More updates are not a faster learning algorithm. A larger decoder is not an equal-capacity mechanism result. Changing representation and learning method together can be a useful system result but cannot isolate their causes without additional controls.

The initial learning-method language is typed and intentionally small: schedule expressions over committed update/exposure counters; replay/frontier sampling weights; admitted objective coefficients; bounded clipping/normalization/preconditioning transformations; and versioned architecture options already implemented by the engineering program. A proposal contains an abstract syntax tree, parameter bounds, eligibility scope, expected benefit, predicted cost, failure conditions and comparison protocol reference.

Validate dimensions, finite values, domain errors and required state. For example, a per-parameter transformation must declare its state tensors and initialization, preserve shape, and have a serializable update rule. A schedule may read training counters and allowed controller metrics, but not sealed accuracy. A data selector may choose among eligible training records, but cannot turn a rejected source trainable. The interpreter exposes no network, shell, arbitrary imports or evaluator mutation. This is the first tractable method search space, not a claim that those knobs span all possible intelligence algorithms.

## 3. Meta-episodes and learning efficiency

A `MetaEpisode` contains a novel task family/mechanism, support experience, a fixed adaptation allowance, a held-out query set and a protected retention set. Support is visible to the adapting learner. Query/retention labels are held by the independent examiner. Store mechanism grouping so the same underlying task cannot appear as support in one supposedly independent query split.

For a method A and a task j, record the adaptation curve `S_j(b)` at preregistered consumed-budget points b. Measure terminal query success, area under the score-versus-budget curve, retained old capabilities and actual resource vector. The budget axis must have a declared meaning, such as admitted examples or device seconds; report other costs separately. Compare method candidates using the master's resource predicate.

Define a proposed meta-objective:

```text
J(A) = mean_j AUC_j(A, fixed_budget_grid)
       - lambda_ret * mean_j protected_regression_penalty_j
       - lambda_fail * invalid_or_unfinished_fraction
```

Primary publication still requires the separate acquisition, retention and resource gates; a weighted scalar cannot hide a protected-family failure. AUC integration uses the same grid and interpolation rule for every treatment. A missing late measurement is not omitted favorably: handle it as a declared failure or conservative score under the protocol.

To isolate a proposed method change at generation i, clone the **same** accepted starting weights/optimizer-compatible state and admitted support ordering for parent method and candidate method, with explicitly independent training seeds where required. Run both on matched meta-tasks. If the new method requires incompatible state, initialize the affected state under a declared migration and apply the corresponding control. Never compare a fresh child against an older parent that received less support while calling the result method improvement.

For representation transfer, conduct a separate comparison: different prior training experience with the same downstream adaptation method and budget. This measures useful learned representation rather than a changed optimizer. Both effects may matter; their receipts must remain distinguishable.

## 4. Learning to propose useful changes

Build a training-only `MethodExperience` table. Each row contains the public learner summary, a proposed method, validation result, preregistered predicted gain/cost, actual meta-training outcome, and evidence identities. Include failed and rejected proposals. A selected archive of only successful changes would teach unrealistic proposal priors and conceal search cost.

The first BRAMASTRA proposer learns the method language through qualified examples, then ranks/proposes candidates conditioned on its observed failure pattern and resource allowance. Proposed losses are masked syntax/field likelihood, pairwise ranking of **measured** candidate outcomes under matched settings, and calibration of predicted gain. Ranking pairs require comparable starting states, task distribution and budgets; unrelated benchmark scores cannot become a preference pair.

A later outcome-trained proposer can use a bounded policy objective whose reward comes from independent meta-training results minus declared proposal/evaluation cost. Keep its behavior snapshot, proposal probabilities and update eligibility as explicit as the task-level policy. Do not train it on confirmation results. Meta-training environments are part of the learning process, even when they contain a nested evaluation loop.

Store proposal uncertainty and an abstain/no-change option. If all candidates are unsupported, retaining the parent is correct. The system should learn to reject attractive but invalid ideas rather than generating a compulsory change every cycle. Track proposal validity, useful-proposal rate, search cost per accepted change and realized-versus-predicted gain.

## 5. A complete generation transaction

```text
G_i starts with accepted learner L_i and frozen evidence policy
L_i receives allowed failure/capability summaries from meta-training
L_i proposes method candidate P_i in the typed language
validator rejects malformed/out-of-scope proposals before training
compiler produces method A_i_candidate with exact identity
orchestrator clones matched parent/candidate adaptation lineages
authorized meta-training comparisons produce complete receipts
candidate selection uses meta-validation under its declared reuse policy
fresh confirmation compares the chosen candidate with the parent method
chief records accept/reject/inconclusive from immutable evidence
if accepted, publish L_(i+1) and its migration/provenance
L_(i+1), not a substituted external proposer, begins the next generation
```

No actual generation training is authorized by this packet. Implement the transaction using fixtures with a separate registry. The original M12 guards apply to every nested lineage and parent publication. A fixture cannot be promoted by renaming its evidence class, and a token string claiming to be a checkpoint ID is not proposer authentication.

`GenerationReceipt` binds proposer checkpoint, proposer origin, parent method, candidate AST/source hash, compiler version, task/split identities, support exposure, all attempted candidates, consumed resources, selected candidate, uncertainty and chief approval. It links the predecessor receipt and includes explicit migration state. The entire failed search is charged, not only the successful final method. A crash or rejection leaves the last accepted learner usable.

Freeze the proposer checkpoint, allowed memory snapshot, method-experience archive identity/cutoff and exposure ledger before each generation's proposals. Bind them to the receipt and paired controls. Updating the proposer or archive after candidate selection creates a new generation; it cannot supply evidence for the old frozen-proposer comparison. If a successor has additional proposal-training experience, the fixed-proposer and ordinary-training controls receive the corresponding declared resource/exposure comparison. Do not attribute extra hidden training to a better proposal algorithm.

## 6. Preventing a misleading recursive result

Use distinct meta-training, reusable meta-validation and fresh confirmation pools. The proposer can learn from meta-training feedback. Repeated candidate selection against meta-validation consumes that pool's independence; report its reuse. Confirmation labels never return as training examples or detailed failure prompts. If the owner chooses to study a confirmation failure, retire that pool from future independent claims and create a new one.

Three accepted generations can serve as an initial **bounded** recursive-improvement demonstration when each satisfies the preregistered policy, the successor is actually used to propose the next change, and protected capabilities remain within bounds. It is not evidence of indefinite improvement, acceleration without limits, or AGI. Report every rejected/intermediate generation and whether proposal quality or future-learning efficiency improves across the chain.

Required controls include a fixed human-designed method with equal total training/search allowance; random valid method proposals; a fixed earlier proposer reused across generations; and a matched system allowed more ordinary training but no method changes. If the successor proposer is no better than the frozen proposer, the result may be useful method search without recursive improvement of the search capability.

Search can overfit the method benchmark. Add new mechanism families and representations for confirmation, and keep final query tasks outside the proposal archive. Report sensitivity to starting weights, task distribution and support size. A good method for one toy family remains a family-specific result.

## 7. Moving beyond the first method language

When the typed language becomes the measured bottleneck, a later source-proposal stage may let BRAMASTRA generate a bounded patch to an isolated candidate implementation. The patch must specify interfaces, state migration, expected invariants and a falsifiable learning claim. Existing independent tests remain frozen; candidate-authored tests are additional evidence and cannot replace them.

The engineering executor reviews and runs the patch in an isolated environment with explicit filesystem/time/output limits. No live parent, evaluator, resource ledger, credentials or unrelated repository is writable by the candidate. Compilation, static checks, non-learning semantic tests and bounded numerical checks precede any allocated training comparison. A patch proposed and substantially repaired by another AI is recorded as assisted, not autonomous BRAMASTRA invention.

This stage can in principle propose representations, memory algorithms, loss terms or learning rules beyond preset coefficients. It requires a separate work order and allocation after M24's basic provenance and method-evaluation loop is correct. The reason to defer live execution is missing validated machinery and budget, not a claim that algorithm invention is outside the AGI objective.
